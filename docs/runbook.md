# RoomBook: експлуатація

## Межа перевірки

Локальні сценарії в `ops/container/` створюють окрему Docker-мережу й тестову БД та видаляють лише створені ними контейнери. Production-мережу, TLS, офісні CIDR, сховище секретів і контакти оператора потрібно підтвердити в конкретному середовищі. Локальний smoke не є підтвердженням розгортання.

## Конфігурація

| Змінна / властивість | Значення або правило |
|---|---|
| `ROOMBOOK_IMAGE` | Незмінне посилання на перевірений образ, бажано digest |
| `ROOMBOOK_VERSION` | Версія релізу, потрапляє в подію START |
| `ROOMBOOK_NETWORK` | Уже створена приватна мережа proxy/app/DB |
| `ROOMBOOK_DB_URL` | `jdbc:postgresql://db:5432/roombook`, обов'язкова |
| `ROOMBOOK_DB_USERNAME` | `roombook_app`, обов'язкова |
| `ROOMBOOK_DB_PASSWORD` | Секрет без значення за замовчуванням |
| `ROOMBOOK_FLYWAY_URL` | За замовчуванням DB URL |
| `ROOMBOOK_FLYWAY_USERNAME` | `roombook_owner`, обов'язкова |
| `ROOMBOOK_FLYWAY_PASSWORD` | Окремий секрет власника схеми |
| `ROOMBOOK_ADMIN_USERNAME`, `ROOMBOOK_ADMIN_PASSWORD` | Потрібні, якщо немає активного ADMIN; після bootstrap прибрати із середовища |
| `roombook.business.office-zone` | `Europe/Kyiv`; зміна потребує перегляду семантики збереженого локального часу |
| `roombook.business.work-day-start`, `work-day-end` | `08:00`, `20:00` |
| `roombook.business.slot-grid`, `min-duration`, `max-duration` | `15m`, `15m`, `4h`; цілі хвилини, до 48 слотів у робочому дні |
| `roombook.business.horizon-days` | `90` |
| `roombook.security.password-hash-cost` | `12` у production, `4` лише в тестах |
| `roombook.security.authenticated-session-timeout` | `8h` |
| `server.servlet.session.timeout` | `15m` до входу |
| `server.servlet.session.cookie.secure` | Обов'язково `true` у production; HttpOnly і SameSite=Lax |
| `server.port`, `management.server.port` | `8080`, `8081`; різні, не публікувати в Інтернет |
| Hikari | 10 з'єднань, очікування до 3 с |
| Контейнер | 1 GiB RAM, 2 CPU, heap до 512 MiB, UID/GID 10001, root filesystem read-only, `/tmp` tmpfs 128 MiB |

Секрети передає оператор через захищене середовище процесу. Не зберігати production-секрети в Git, аргументах команд, образі чи загальному `.env`. Production-профіль є типовим; `dev` і `test` не використовуються для релізу.

## Підготовка PostgreSQL 16

1. Створити БД `roombook` із UTF-8 та доступною українською ICU-локаллю; забезпечити `btree_gist` згідно з міграціями.
2. У середовищі адміністративного `psql` задати `ROOMBOOK_OWNER_PASSWORD`, `ROOMBOOK_APP_PASSWORD`, `ROOMBOOK_BACKUP_PASSWORD` та виконати `psql -X -v ON_ERROR_STOP=1 -d roombook -f ops/db/init-production.sql`.
3. Перевірити окремі ролі: власник виконує Flyway; застосунок має SELECT/INSERT/UPDATE, але не DELETE/DDL; backup має читання. Таймаути ролі застосунку: lock 5 с, statement 10 с.
4. `ops/db/init.sql` містить відомі тестові паролі й призначений для Testcontainers. Не запускати його в production.

Bootstrap після міграцій: активний ADMIN існує — без змін; заданий користувач існує — підвищення, активація й заміна пароля; користувача немає — створення. Якщо немає активного ADMIN і облікових даних, старт завершується помилкою. Readiness включає стан завершення запуску та доступність БД.

## Збірка і реліз

1. Виконати `mvn test`: обидві зони запускаються автоматично. На цій Windows-машині еквівалент — `pwsh -File ops/test.ps1`.
2. Після успішних тестів виконати `mvn -DskipTests package` або `pwsh -File ops/package.ps1`. `-Online` потрібен лише для заповнення локального кешу інструментів пакування.
3. `docker build -t roombook:verify .`, потім `python ops/container/smoke.py`. Зберегти результати й digest релізного образу. Образ базується на Temurin 21.0.13+9, зафіксованому digest у Dockerfile.
4. Зняти передрелізну копію БД. Перевірити її читання, розмір і шифрування. Зберегти поточний image digest, версію схеми та конфігурацію без секретів.
5. У вікно релізу зупинити приймання змін, зупинити попередній інстанс і запустити новий через `docker compose up -d`. Інстанс один; сесії в пам'яті, після перезапуску потрібен повторний вхід.
6. Дочекатися readiness UP; перевірити вхід, зайнятість, українське сортування та подію START із версією схеми. Лише після цього повернути трафік.
7. Якщо міграція чи smoke не пройшли, не подавати трафік. Для відкату несумісної схеми відновити передрелізну копію в окрему чисту БД, застосувати ролі, запустити попередній образ і перевірити readiness та інваріанти. Не запускати старий код поверх невідомої нової схеми.

Щомісяця та після оновлення JDK/Spring перебудовувати образ, оновлювати перевірений digest, запускати часові тести TS-05 і container smoke. Дані tzdb оновлюються разом із runtime-образом.

## Reverse proxy і мережа

TLS завершує довірений reverse proxy. Він має додавати HSTS `max-age=31536000`, перезаписувати `X-Forwarded-Proto`, `X-Forwarded-Host`, `X-Forwarded-For` і `X-Request-Id`, а не довіряти клієнтським значенням. Застосунок використовує forwarded headers лише за мережевої недоступності його порту ззовні.

Дозволити доступ лише з погоджених офісних мереж/VPN. Окремо обмежити частоту `/login` та `/api/v1/csrf` і розмір тіла запиту. Початкові ліміти для перевірки оператором: 5 запитів/хв на login та 30/хв на csrf з малою чергою burst. Таймаут proxy read має перевищувати 10 с statement timeout, наприклад 15 с. Конкретні ліміти підтверджуються навантаженням і кількістю людей за спільною IP-адресою.

`compose.yaml` не публікує порти на хості. Порт 8081 доступний лише оператору/монітору в приватній мережі. На ньому відкриті GET health і metrics; health не показує деталей. Проби: `/actuator/health/liveness` кожні 10 с, `/actuator/health/readiness` щохвилини. Синтетичний GET `/login` виконується через HTTPS-проксі з іншого хоста.

## Журнали

JSON ECS у stdout, UTC, requestId і структуровані поля подій. Запити містять method/path/status/durationMs без query/body. Очікувані конфлікти — INFO; помилки входу — WARN з обрізаним логіном; неочікувані помилки — ERROR зі стеком та ознакою LOCK_TIMEOUT/POOL_TIMEOUT за потреби. Журнали операційні, не незмінний аудит. Обмежити доступ і налаштувати ротацію на хості.

## Відновлення і моніторинг

На хості БД потрібні PostgreSQL client tools, Python 3.11+ із tzdata й GnuPG. `ops/backup/backup.py` запускає custom-format `pg_dump` від `roombook_backup`, перевіряє `pg_restore --list` і розмір не менший за половину попередньої успішної копії. Копія шифрується OpenPGP/AES256 до запису у віддалене сховище; відкритий тимчасовий файл видаляється також при помилці. Destination має бути окремим off-host mount, підтвердженим оператором. Ключ: щонайменше 32 випадкові байти, окреме захищене сховище поза каталогом копій, доступ лише backup-оператору; резерв ключа також окремий.

Шаблони systemd у `ops/backup/` запускають копіювання о 01:00 Europe/Kyiv. У `backup.env` налаштувати PGHOST, PGPORT, PGDATABASE, PGPASSWORD ролі backup та версії образу/схеми. Права файлу 0600. Зберігаються 30 останніх daily-копій; prerelease — 30 днів. Метадані містять час, версії, розмір і SHA-256 шифротексту. Невдача пише BACKUP_FAILED, зберігає попередній lastSuccess і ставить lastResult=failed.

Відновлення:

1. Зафіксувати початок інциденту, зупинити трафік і зміни, вибрати перевірений image digest та відповідну копію. Перевірити SHA-256 шифротексту за захищеними метаданими.
2. На чистому хості PostgreSQL 16 створити БД і ролі через `init-production.sql`. Отримати ключ окремим каналом, розшифрувати `gpg --batch --pinentry-mode loopback --passphrase-file KEY --output restored.dump --decrypt COPY.gpg` у захищений локальний тимчасовий файл.
3. Виконати `pg_restore --list`, потім `pg_restore --exit-on-error -d roombook restored.dump` від адміністратора БД. Ролі власника об'єктів мають існувати. Виконати всі `ops/audit/inv-*.sql`: кожен має повернути нуль рядків.
4. Запустити відповідний образ із новими секретами, дочекатися readiness UP, перевірити вхід, зайнятість, сортування та відновлені бронювання. Зафіксувати час до готовності. Межа RTO — 2 години, ціль — 1 година. Видалити відкриту копію, повернути трафік і створити нову зашифровану копію.

Локальна репетиція: `python ops/backup/rehearse.py`. Вона використовує окремий чистий контейнер БД, перевіряє реальне шифрування/дешифрування, відновлення, аудит і вхід. Це не вимірювання перенесення production-обсягу на фізично інший хост.

Монітор запускається щохвилини на окремому від застосунку хості: `ops/monitoring/monitor.py`. Проби readiness і HTTPS `/login` мають завершитися зі статусом 200 за 3 с. `collect_host.py` на хості БД/копій експортує свіжий JSON стану копіювання, використання обох томів і NTP; доставку цього файлу монітору налаштовує оператор. Дані старші за 3 хв дають HOST_STATE_STALE.

У вікні 07:00–21:00 Europe/Kyiv три недоступні хвилини поспіль дають UNAVAILABLE_3_MINUTES. Також сигналізуються копія старша за 26 год, невдала копія, використання тому понад 80%, несинхронізований NTP. Пропущені хвилини рахуються недоступними в доступності month-to-date; окремо виводиться кількість пропусків. Код виходу 2 та JSON alerts потрібно під'єднати до погодженої системи сповіщень; скрипт сам не надсилає повідомлень зовнішнім адресатам. Доставка й адресат мають бути підтверджені оператором.
